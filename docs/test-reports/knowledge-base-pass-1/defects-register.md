# Knowledge Base programme - defects register

Written for every developer or agent working on the programme, and for the owner. English.

This is where a defect found **during** the programme is written down, whoever finds it (an agent while preparing a test, the owner in a human test, a lot's own tests) and whether or not the Knowledge Base (KB) caused it. It complements, and does not replace, the bug register of the first human pass (`docs/test-reports/human-acceptance-pass-1/03-bug-register.md`, BUG-nn), which stays the home of the defects found there.

## The rule (owner instruction, 9 October 2026)

1. **Every defect is recorded here, in the lot where it is found**, with its evidence: the exact question, the selection, what was answered, what was expected, and the file or code it points to. A defect that exists only in a chat is lost.
2. **Every defect is analysed against the KB roadmap** before the lot ends: *does it get in the way of lots still to come, or will it?* The analysis is written in the "Effect on the KB" column, with the lot numbers concerned and the reason. "No effect" is an answer; "not analysed" is not.
3. **A defect that blocks, or will block, the KB is fixed first**, in its own branch and pull request (`fix/kb-<topic>`, base `kb/integration`), before the lot that needs it. The agent that finds it stops, tells the owner, and proposes the fix; it does not build on top of it.
4. **A defect that does not interfere is not fixed in the middle of the programme.** It stays in this register with status `deferred`, so the programme keeps its focus and each lot stays reviewable.
5. **At the end of the programme (lot 11), the agent proposes a targeted fix battery** for every `deferred` defect: one list, grouped, with the risk and the test that will prove each, ready for the owner to accept and schedule. The owner has said these fixes **must** be done after the KB, not forgotten. Lot 11's final report cannot be signed off while a `deferred` row has no proposed fix.
6. **Any agent that touches a file named in a `deferred` row must re-read that row** and say in its lot report whether the defect still holds or became a blocker.
7. **Keep it honest.** A defect found by running something is recorded as observed, with the command or the question. A hypothesis about the cause is marked as one.

Status values: `open` (just found, effect not yet analysed), `blocking` (fix before the named lot), `deferred` (post-KB fix battery), `fixed` (with the commit or pull request), `not-a-defect` (kept for the record, with the reason).

## How lots use this file

- At the start of a lot: read every row that is not `fixed` or `not-a-defect`, and the rows that name a file your lot touches.
- During a lot: add a row the moment a defect is seen. Do not wait for the report.
- At the end of a lot: the lot report's "Open questions" lists the rows added or changed, with their effect on the next lots; `docs/SESSION-KB-STATUS.md` says whether any row is `blocking`.
- Lot 11: turn every `deferred` row into the proposed fix battery (workflow section 2.4).
